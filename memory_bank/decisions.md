## ADR-001: Использование Sigma-Fractal вместо классического Grid

**Дата:** 2026-01-20  
**Статус:** Принято

### Контекст
Классический Grid Bot работает только в боковике. В тренде накапливает убыточные позиции.

### Решение
Интегрировать систему Билла Вильямса для определения режима рынка:
- RANGE → Grid
- TREND → Направленная торговля
- SQUEEZE → Ожидание

### Последствия
- ✅ Бот адаптируется к рынку
- ✅ Меньше убыточных сделок в тренде
- ⚠️ Сложнее логика
- ⚠️ Больше параметров для оптимизации

## ADR-002: Alligator + Bollinger вместо только Alligator

**Дата:** 2026-01-20  
**Статус:** Принято

### Контекст
Оригинальная стратегия Вильямса использует только Alligator. Мы добавили Double BB.

### Решение
- **BB (1σ + 2σ)** — зоны для фильтрации фракталов
- **Alligator** — подтверждение тренда

### Почему
1. BB даёт чёткие уровни для Key Fractals
2. Alligator медленный, BB быстрее реагирует на squeeze
3. Комбинация даёт меньше ложных сигналов

## ADR-003: SqueezeDetector через BB Width Percentile

**Дата:** 2026-01-20  
**Статус:** Принято

### Контекст
Нужно определять низкую волатильность для входа перед пробоем.

### Решение
- Считаем BB Width = (upper - lower) / middle * 100
- Сравниваем с историческими значениями (percentile 25)
- Если текущий width < 25-й перцентиль → SQUEEZE

### Параметры
- `squeeze_percentile = 25` (можно настроить)

## ADR-004: Grid границы = Key Fractals > BB 1σ

**Дата:** 2026-01-20  
**Статус:** Принято

### Контекст
Нужно определить верхнюю и нижнюю границу Grid.

### Решение
1. **Приоритет:** Последние Key Fractals (UP и DOWN)
2. **Fallback:** Если нет ключевых фракталов → используем BB 1σ

### Почему
- Key Fractals = реальные уровни поддержки/сопротивления
- BB 1σ = статистическая граница, но менее надёжная

## ADR-006: Файловый кэш для OHLCV данных

**Дата:** 2026-01-20  
**Статус:** Принято (временно)

Нужно хранить исторические данные для бэктестов и анализа.
Проект планируется перенести на VPS.

### Решение
- **Сейчас:** Pickle-файлы в `./cache/` (через `DataLoader`)

### Формат кэша

### Почему
- Простота на этапе разработки
- Нет зависимости от БД локально
- Легко перенести на VPS

- [ ] Добавить `DatabaseDataLoader` как альтернативу `DataLoader`

## ADR-007: Процесс разработки через связку Codex + RooCode

**Дата:** 2026-03-11  
**Статус:** Принято

### Контекст
Разработка ведётся в WSL, затем синхронизация в GitHub и проверка на VPS.  
Нужен стабильный агентный процесс: архитектура и ТЗ от Tech Lead, реализация задач кодером.

### Решение
1. Зафиксировать единый workflow в `docs/AGENT_DEVELOPMENT_WORKFLOW.md`.
2. Использовать RooCode как **Coder** по атомарным задачам из tasklist.
3. Использовать Codex как **Tech Lead + Reviewer** (Spec/Plan/Review/Backlog).
4. Импортировать и адаптировать skills из `bybit_options` и `defi_agents` в `.agent/skills/`.
5. Каноничный Memory Bank для проекта: `memory_bank/*` (с синхронизацией `docs/memory-bank/*`, если используется SDD-контур).

### Последствия
- ✅ Единый формат handoff задач в RooCode
- ✅ Меньше расхождения между архитектурой и реализацией
- ✅ Быстрый старт DEX LP migration через готовые skills (range ops, risk, alerts)
- ⚠️ Нужно поддерживать skills и workflow в актуальном состоянии при изменении архитектуры

## ADR-010: In-Project Storage for Implementation Plans

**Дата:** 2026-03-11  
**Статус:** Принято

### Контекст
Gemini/Claude (в среде Antigravity) могут создавать `implementation_plan.md` во внешних директориях (например `~/.gemini/...`), что приводит к потере видимости и рассинхрону документации.

### Решение
1. Все проектные планы и артефакты хранятся только в репозитории `bybit_grid_bot`.
2. `implementation_plan.md` сохраняется в `docs/plans/` (или эквивалентный `<ticket>-plan.md` в той же директории).
3. Внешние файлы считаются временными и не являются SSOT.

### Последствия
- ✅ Единый источник истины для планирования внутри проекта
- ✅ Упрощается handoff между агентами и ревью
- ⚠️ Нужно вручную переносить план, если инструмент создал его вне проекта

## ADR-011: Product Focus Narrowing to Solana + Meteora

**Дата:** 2026-03-11  
**Статус:** Принято

### Контекст
Нужно перейти от общего DEX LP контекста к конкретной практической цели: находить пары и диапазоны для LP-стратегии в одной экосистеме, чтобы быстрее получить рабочий MVP.

### Решение
1. MVP-фокус: **Solana + Meteora**.
2. Основной сценарий: scanner + decision/alert engine для входа по Sigma-Fractal логике.
3. Таймфреймы стратегии: D1 по умолчанию, H4 после пробоя ключевого фрактала.
4. Stage 1: только входные сигналы; сопровождение/закрытие — вручную пользователем.

### Последствия
- ✅ Сужение scope ускоряет путь к рабочему MVP
- ✅ Ясные критерии входных сигналов (`TREND_UP_ALERT`)
- ⚠️ Нужны уточнения по типу пулов Meteora (DLMM/другие) и baseline risk limits

## ADR-012: Meteora DLMM + VPS Read-Only MVP Mode

**Дата:** 2026-03-11  
**Статус:** Принято

### Контекст
Для ускорения запуска нужен узкий и операционно простой контур MVP без on-chain исполнения.

### Решение
1. Целевой DEX-контур: **Solana / Meteora DLMM**.
2. MVP-режим: **scanner + decision engine** (read-only/paper).
3. Фильтры (ликвидность/объём/возраст) реализуются сразу, но в режиме `TEST` не блокируют сигналы.
4. Развёртывание ориентировано на VPS (службы/таймеры, логи, алерты).

### Последствия
- ✅ Быстрый запуск без риска исполнения транзакций
- ✅ Сбор статистики фильтров до включения строгих блокировок
- ⚠️ Нужно отдельно утвердить production-пороги risk limits перед режимом `STRICT`

## ADR-013: Baseline Filter/Risk Defaults for Scanner Modes

**Дата:** 2026-03-11  
**Статус:** Принято (как стартовые конфигурационные значения)

### Контекст
Нужны стартовые пороги для фильтров и risk checks, чтобы перейти от полностью свободного теста к управляемому режиму принятия решений.

### Решение
Использовать три режима:
1. `TEST` — без блокировки входного сигнала (только логирование и reason codes).
2. `SOFT` — пороги влияют на score/ранг.
3. `STRICT` — пороги блокируют входной сигнал.

Стартовые значения:
- `SOFT`: liquidity >= 50k, volume24h >= 25k, pool_age >= 3d, slippage_open <= 120 bps.
- `STRICT`: liquidity >= 200k, volume24h >= 100k, pool_age >= 14d, slippage_open <= 80 bps.

### Последствия
- ✅ Есть измеримая основа для paper-валидации.
- ✅ Можно накапливать статистику в `TEST` без потери сигналов.
- ⚠️ Значения требуют калибровки после первых циклов сканирования.

## ADR-014: Stage 1 is Alert-Only (Manual Pool Creation)

**Дата:** 2026-03-11  
**Статус:** Принято

### Контекст
Для первого релиза важно быстро получить рабочий сигнал и операционный цикл без рисков автоторговли.

### Решение
1. Stage 1: бот только определяет `TREND_UP` кандидаты и шлёт Telegram сигнал.
2. Бот НЕ открывает/закрывает пул on-chain.
3. Открытие пула выполняется пользователем вручную на основе сигнала и рекомендованного диапазона.
4. В Stage 1 бот не отправляет отдельные exit-сигналы; только входные alerts.

### Последствия
- ✅ Снижение операционного риска на MVP этапе.
- ✅ Быстрее обратная связь по качеству сигналов.
- ⚠️ Контроль исполнения и дисциплина входа остаются на пользователе.

## ADR-015: Codex-Native Agentic SDLC Controls

**Дата:** 2026-07-19
**Статус:** Принято

### Контекст

Существующий агентный контур был построен вокруг обязательного handoff в
RooCode. Для текущей работы нужен проектный процесс, который использует Codex
напрямую, но сохраняет контролируемые границы реализации, независимую проверку
и SSOT-дисциплину.

### Решение

1. Использовать роли Orchestrator → Coder → Reviewer → Verifier в отдельных
   стадиях; в Implementation пишет только один Coder и только в write-set.
2. Сохранить Plan → Spec → Implementation → Review → Verification для
   нетривиальной работы; Review и Verification сделать read-only gates.
3. Адаптировать семь локальных Codex skills из
   `agentic-sdlc-framework`, зафиксировав immutable source revision в
   `.agent/skills.lock.yml`; не переносить hooks, MCP, deploy или CI-автоматику.
4. Обновлять tasklist и memory bank только после verifier verdict `READY`.

### Последствия

- ✅ Процесс не зависит от отдельного RooCode handoff.
- ✅ Снижен риск scope drift и самоподтверждения реализации.
- ✅ У каждого локального skill есть узкая роль и проверяемая metadata.
- ⚠️ Для сложной задачи Orchestrator должен явно формулировать work block и
  разделять стадии, а не выполнять их как один неаудируемый шаг.
